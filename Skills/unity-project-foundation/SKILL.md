# Unity 프로젝트 제작 기반

사용자가 수정할 수 있는 에셋을 남기고, 데이터의 원본과 실행 상태의 소유자를 분명히 한다. 기존 프로젝트에서는 현재 구조와 사용자 편집 내용을 먼저 확인한다. 새 프로젝트에서만 아래 기본 구조를 출발점으로 사용하며, 구조를 맞추려고 기존 폴더를 일괄 이동하지 않는다.

## 먼저 확인할 것

- 해당 프로젝트의 `AGENTS.md`, Unity 버전, 씬·프리팹·데이터 흐름, 실제 진입점을 읽는다.
- 요청이 기획, 에디터 에셋 작성, 런타임 구현, 빌드, 배포 중 어디까지인지 구분한다. 이미 받은 사용자 승인을 반복 요구하지 않는다.
- 원본 프로젝트의 상세 경로 및 관찰 근거는 [프로젝트에서 추출한 근거](references/provenance.md)를 필요할 때 읽는다. 예전 프로젝트의 승인 조건·제목·수치·플랫폼을 새로운 프로젝트의 요구사항으로 취급하지 않는다.

## 신규 프로젝트 기본 구조

```text
Client/                  Unity 프로젝트(Assets, Packages, ProjectSettings)
  Assets/Game/
    Runtime/             게임 규칙·세션·서비스·View/Presenter
    Editor/              임포터·에셋 제작·검증 도구
    Data/Generated/      검증된 원본에서 생성한 런타임 데이터
    Prefabs/             화면·캐릭터·전투 요소의 저장 프리팹
    Art/ Audio/          제작 자산 및 연결
    Tests/               위험한 상태 전이·데이터 계약 검증
GameData/                기획자가 수정하는 원본과 스키마·검증
Server/                  필요할 때만 추가하는 서버와 플랫폼 경계
Planning/                기획·와이어프레임·결정·검토·검증 근거
```

`Runtime`은 `Editor`를 참조하지 않는다. 외부 SDK는 실제 연동 시 플랫폼 어댑터로 격리한다. 순수 로컬 MVP에 로그인·서버·원격설정·범용 프레임워크를 미리 만들지 않는다.

## 데이터와 저장

1. 밸런스·상점·스테이지·문구마다 단일 편집 원본을 정한다. Excel을 사용하면 코드나 생성 SO에 같은 값을 다시 하드코딩하지 않는다.
2. 안정적인 ID, 필드 타입, 단위, 허용 범위, 필수값과 참조 관계를 정의한다. 행 번호나 번역 문자열을 영구 ID로 사용하지 않는다.
3. 임포터는 모든 시트의 중복 ID·외래키·범위·단위를 먼저 검증한다. 전체 검증 실패 시 기존 정상 산출물을 보존하고 파일·시트·행·열이 있는 오류를 반환한다.
4. 검증 성공 후 결정적으로 SO/JSON을 생성하고 manifest에 schema/data 버전과 필요한 출처를 기록한다. 생성 데이터에는 수동 편집 경고를 남긴다.
5. 설정 데이터는 읽기 전용으로 취급한다. 전투 HP·쿨타임·버프는 별도 런타임 인스턴스에 둔다. 공유 SO를 플레이 중 변경해 다음 전투에 상태가 새지 않게 한다.
6. 저장에는 schemaVersion과 마이그레이션을 둔다. 실행 상태, 콘텐츠 데이터, 영구 진행을 분리한다. 계정 전환이 있으면 캐시도 계정 범위로 격리한다.
7. 보상·구매·결과 저장은 중복 콜백에 대해 한 번만 처리한다. 서버 권위가 필요한 기능은 영수증/거래 ID 검증과 재처리 계약을 먼저 정의한다.

Excel을 채택하면 [원본·카탈로그·저장 계약](references/data-contract.md)의 표 형식을 필요에 맞게 사용한다. 원본 파일은 책임별로 나눌 수 있지만 소규모 MVP에 빈 도메인 파일을 미리 만들지 않는다.

## 프리팹과 에디터

- 화면과 조정 가능한 캐릭터·이펙트는 실제 `.prefab`/`.asset`/`.unity`로 저장한다. 런타임 코드로 UI 계층을 통째로 재생성해 에디터 편집을 무효화하지 않는다.
- 빌더는 최초 생성 또는 명시된 부분 수정에 사용한다. 수동 수정된 대상은 부분 변경을 우선하고, 해당 자산 전체 교체가 사용자 요청에 명확히 포함된 경우에만 전체 재생성한다. 변경 전후 참조와 영향 범위를 기록한다.
- 의존성은 직렬화 필드와 명확한 조립 지점으로 연결한다. 누락 참조를 검증하고 임의의 `Find` 연쇄로 숨기지 않는다.
- 반복 적용은 안정적이어야 한다. 이미 올바른 값은 다시 쓰지 않고 GUID·사용자 조정·다른 패널을 보존한다.
- 생성기 동작을 `CreateMissing`, `MigrateExisting`, `Validate`로 구분한다. 누락 참조 검증 실패를 화면 전체 재생성의 이유로 삼지 않는다. 같은 형태의 요소를 추가할 때는 사용자가 조정한 기존 공용 프리팹/요소를 재사용한다.
- 런타임은 저장 프리팹 인스턴스의 상태를 바꾸거나 풀에서 대여한다. 적 스폰과 동적 목록 아이템 생성까지 금지하는 규칙으로 확대하지 않는다.

## 런타임·UI 책임과 패턴

- 게임 세션이 진행 상태·전투 시계·승패를 소유하고, Presenter는 상태를 읽어 View를 갱신한다. UI 타이머가 별도 승패 판정을 하지 않는다.
- 전투 시계와 UI의 unscaled 시간을 구분한다. 일시정지·앱 복귀·배속·씬 전환에서 각 시계의 동작을 정의한다.
- 상태가 적고 분명하면 enum과 명시적 전이로 시작한다. 시작/플레이/일시정지/결과 등 전이 규칙이 늘면 작은 FSM을 사용한다.
- ID 조회는 `Dictionary`, 순서가 있는 패턴·웨이브는 배열/`List`, 중복 방지는 `HashSet`, 순차 처리는 `Queue`를 고려한다. 실제 접근 패턴으로 선택한다.
- 적이 소수면 선형 탐색으로 충분하다. 수백 개의 범위 질의가 측정된 병목일 때만 spatial hash를 도입한다.
- 자주 생성·파괴하는 탄환/VFX만 제한된 Pool을 고려한다. 반환 시 타이머·구독·피격 기록·부모·시각 상태를 초기화하고 최대 수를 정한다.
- 외부 광고·결제·저장은 작은 인터페이스/Adapter로 격리한다. 구현이 하나뿐인 모든 클래스에 추상화 계층을 추가하지 않는다.
- 이벤트 구독은 수명과 함께 해제한다. 재시작·패널 재개방·씬 재진입이 중복 이벤트를 만들지 않아야 한다.

## 제작 흐름과 검증

요구사항과 데이터 계약 → 와이어프레임/상태 흐름 → 최소 플레이 루프 → 저장 프리팹·임포터 연결 → 관련 검증 → 실제 화면/기기 확인 순서로 진행한다. UI와 문구 작업에는 별도 설치된 `game-ui-wireframe-copy`를 함께 쓸 수 있다.

공동 작업이 요청된 경우 담당 범위, 공유 계약, 변경 파일 소유자와 검토 근거를 기록한다. 담당자의 실제 피드백을 받기 전 “검토 완료”라고 쓰지 않는다. 기획 수치와 실측 결과도 구분한다.

검증은 변경의 위험에 맞춘다. 데이터 실패 시 정상 산출물 보존, 보상 중복, 저장 복구, 전투 상태 전이 등은 의미 있는 자동 검사 대상이다. 화면은 대상 비율·Safe Area·긴 문구·최소 기기에서 렌더와 입력을 확인한다. 빌드 성공을 실제 플레이 검증으로 대신하지 않는다.

Unity 실행이 제한되면 가능한 소스·데이터·이전 도구 작성과 정적 검증까지 진행한다. 도구 준비, 에셋 적용, 임포트 실행, 렌더 확인의 완료 여부를 각각 보고한다.
