# v7 피격 백색 효과와 조우 전환 검토

2026-10-21 · 기획용 Canvas 코드와 전투 연결 계약. Unity·GameData는 수정하지 않는다. 담당 제작물은 `Presentation/hit-flash-v7.js`, 이 검토서와 `Evidence/Presentation-v7/`의 피격·회피 비교 이미지2개다. 기존 core 파일 연결은 총괄이 수행한다.

## 1. 피격 한 번에 캐릭터만 하얗게 변한다

| 확인된 명중 이후 | 표현 |
| --- | --- |
|명중 전|원본 색|
|0~45ms|현재 캐릭터 프레임의 불투명 픽셀을 흰색으로 표시|
|45~120ms|흰색 비율을1→0으로 줄여 원본 색으로 복귀|
|120ms 이후|원본 색. 백색 효과 종료|

플레이어와 MVP 적5종에 같은 곡선을 적용한다. 캐릭터 시트에 포함된 무기·옷도 함께 하얗게 변한다. 투명한 빈 곳·배경·HUD·외부 참격·별도 파편은 덮지 않는다. 캐릭터 사각 영역을 흰 사각형으로 채우거나 월드 전체의 밝기를 바꾸지 않는다.

현재 일반 피격 표현180ms는 그대로다. 명중200ms인 플레이어 공격에서는 적의 흰색 효과가200~320ms, 피격 자세는200~380ms다. 공격 간격500ms, 회피 유효160ms·복귀100ms·완벽60ms, 기절 누적·시간·무적은 바꾸지 않는다. 백색 효과는 치명타 여부와 무관하게 같은 길이를 사용한다.

명중 판정 소유자가 대상과 해당 피해 사건의 시작 시각을 정한다. 한 피해 사건에 한 번 시작하며, 렌더링·스크럽·입자 개수·시트 프레임 변경은 새 사건을 만들지 않는다. 여러 화살이나 가시가 한 패턴의 단일 타격을 표현하면 플래시도 한 번이다. 실제 별개의 후속 피해를 다시 입었을 때에만 그 사건 시각에서 새 효과를 시작한다. 동일 사건이 중복 전달되면 기존 표시 시작 시각을 유지한다.

## 2. 코드 계약과 캐시

`HitFlashV7`는 상태 없는 시간 샘플러와 캐릭터 그리기 도우미다. 내부 타이머·전투 이벤트·피해 계산·입력 처리가 없다. 프리뷰는 `elapsed = previewTime - confirmedImpactTime`을 전달하므로 뒤로 스크럽해도 같은 그림을 다시 볼 뿐이다. 게임 연결 시에는 전투가 전달한 사건 시각을 사용하고, 일시정지 중 그 나이가 증가하지 않게 기존 표시 시계 정책을 따른다.

```js
HitFlashV7.opacity(ageMs); // 명중 전/120ms 이후0, 0~45ms1
HitFlashV7.drawRegion(ctx, sheet, [sx, sy, sw, sh], [dx, dy, dw, dh], ageMs);
HitFlashV7.drawClip(ctx, clipId, index, x, foot, height, ageMs);
HitFlashV7.drawSprite(ctx, atlasName, x, foot, height, ageMs);
```

이 함수들은 **기존 캐릭터 draw를 대체한다**. 원본을 그린 뒤 다시 이 함수를 호출하는 방식이 아니다. 두 번 겹쳐 그리면 반투명한 외곽 픽셀이 진해질 수 있다. `drawClip`은 현재 `motions-v6.js`의 프레임 crop·피벗·체급 스케일·정수 반올림을 사용한다. `drawSprite`는 현재 대기 `on_00`의 `hero-v5-idle` 대체와 기존 아틀라스 좌표를 따른다. 새로운 상태 전이·사망 분해·와이어프레임을 소유하지 않는다.

흰 시트는 원본 이미지 객체별 `WeakMap`에 한 번 생성한다. 원본을 별도 Canvas에 그린 뒤 `source-in`으로 RGB만 흰색으로 바꾸므로 원본 alpha가 그대로 남는다. 시트는 불변으로 취급하고, 이미지 객체 또는 크기가 바뀌면 새 캐시를 사용한다. 프레임마다 전체 흰 시트를 재생성하지 않는다.

프레임을 확대하기 전에 별도 임시 Canvas로 해당 셀만 분리한다. 중간 색 복귀는 그 셀에서 `source-atop`으로 흰색 비율만 섞어 원본 alpha를 유지한다. 그 뒤 현재 월드 변환 안에서 한 번 그린다. 임시 Canvas는 크기가 같으면 재사용한다. 대상 컨텍스트는 `save/restore`로 alpha·합성·필터·변환·스무딩 상태를 보존한다.

브라우저는 `document.createElement('canvas')`를 사용한다. 최소 DOM만 있는 기존 `render-v6-offline.mjs` 방식에서는 스크립트를 읽은 뒤 다음 한 줄을 주입한다. 이 설정은 캐시를 초기화하므로 전체 렌더 시작 전에 한 번만 수행한다.

```js
vmContext.HitFlashV7.setCanvasFactory(createCanvas);
```

도우미는 `globalThis.HitFlashV7`와 `window.HitFlashV7`에 같은 API를 노출한다. 문서의 script는 `canvas-base.js` 뒤, `app.js` 앞에 추가한다. 실제 `drawClip` 호출 전에는 모션 파일의 `PL_BY_ID`, `PL_REF`와 이미지 로드가 완료되어야 한다. 오프라인 렌더 목록에도 새 파일을 명시해야 한다.

## 3. 기존 코드의 연결 위치

| 실제 진입점 | 전달할 나이와 연결 |
| --- | --- |
|`drawMonsterHit(ctx,targetId,after)`|기존 `drawClip`을 `HitFlashV7.drawClip(...,after)`로 대체. 기존180ms 활성 여부와 프레임 선택은 유지. 미제작 fallback도 `drawSprite(...,after)`로 대체|
|`heroMotion(ctx,'hit',time,dur)`|피격 상태의 현재 프레임만 `HitFlashV7.drawClip(...,time)`로 표시. 다른 상태, 특히 사망 분해의 기존 `drawHeroClip`은 그대로 유지|
|`motionFrame`의 적 `state==='hit'`|선택한 피격 프레임을 같은 도우미와 `time`으로 표시. `drawMonsterHit`를 호출하도록 합쳤다면 추가로 두 번 적용하지 않음|
|`warningFrame`의 실패 회피|`success===false`일 때에만 `age=time-duration`. 현재 플레이어 그림을 `drawSprite(...,age)` 또는 선택한 실제 피격 프레임으로 대체. 성공한 일반/완벽 회피에는 효과0|
|적 공격 준비·발동 중 실제 피해|핵심 공격 자세를 유지하고 그 현재 프레임의 RGB만 바꿈. 백색 효과를 위해 별도 피격 클립으로 강제 교체하거나 예정 공격을 취소하지 않음|

명중 앞175~200ms의 외부 참격 예고에는 적 플래시가 없다. 성공 회피의 종 게이지 상승·기절 효과에도 새 피격 플래시를 시작하지 않는다. 사망·실제 기절의 상태 우선순위는 유지하며, 이 도우미가 대기나 피격 자세로 되돌리지 않는다. 죽은 캐릭터나 다음 스폰으로 이전 피해의 나이가 넘어가지 않도록 표시 상태는 해당 대상에만 속한다.

## 4. 자체 검증 결과

현재 v6의 실제 온 피격과 적5종 clean 피격에서 같은 원본 프레임을 −1/0/82.5/120ms로 그려24개 결과를 비교했다. 아래 항목은 오프라인 Canvas 검사에서 통과했다.

- 실제6종의 기존 그리기와 모든 출력 alpha가 일치한다. 피벗·체급·프레임 crop도 유지한다.
- 완전 불투명·alpha128·완전 투명 픽셀을 섞은 검사에서 alpha가 변하지 않고 RGB만 흰색으로 섞인다.
- 0ms에 불투명 픽셀은 흰색이고,120ms에는 기존 원본 출력과 픽셀이 완전히 일치한다.
- 원본 시트 자체가 바뀌지 않고 같은 원본의 흰 시트를 재사용한다.
- 투명한 외곽과 배경, 호출자 컨텍스트의 alpha·스무딩 상태를 보존한다.
- 브라우저형 Canvas 생성 함수와 `document.createElement` 없는 오프라인 factory 주입 경로가 같은 결과를 낸다.

검사 중 오프라인 Canvas가 전체 Image 시트와 전체 Canvas 시트를 확대할 때 서로 다른 경계 픽셀을 선택하는 차이를 발견했다. 셀을 먼저 분리하는 현재 방식으로 수정한 뒤 실제6종의 alpha 일치를 다시 확인했다. [비교 이미지](../Evidence/Presentation-v7/hit-flash-proof.png)의 네 열은 원본·완전 흰색·절반 복귀·완전 복귀다. 직접 보았을 때도 배경 사각형 없이 캐릭터 실루엣만 바뀐다.

이는 개별 도우미와 기존 자산의 검수다. 총괄의 v7 core 연결·브라우저 화면·실제 입력·Unity 플레이 검증을 대신하지 않는다. 무기색·후드·기존 피격 원화의 정리 항목도 이 색 효과만으로 해결되었다고 하지 않는다.

## 5. 추가 요청: 1초 질주와 Stage 조립 표시

총괄과 합의한 신규 이동은960px/1000ms다. 기존480px/1200ms의400px/s에서960px/s로2.4배 빨라진다. 처치 후 전진은 플레이어x500 고정, 바닥과 깊이별 배경 이동이며 공격의 접근·복귀와 분리한다. 반려된 v6 질주는 새 동작의 fallback으로 조용히 다시 사용하지 않는다. 전진 끝에는 월드 이동을 멈추고 다음 적이 기준x900에 정착해야 한다.

총괄이 채택한 전환 순서는 아래와 같다. 조립 이후 유지·소멸 길이는 전투 판정창을 바꾸는 값이 아니라 검토용 표시 시간이다.

| 일반 적 처치 기준 | 연출·잠금 |
| --- | --- |
|0~550ms|기존 도트 분해. 남은 공격 복귀를 이 구간과 겹쳐 완료|
|550~1550ms|1초 전력 질주. 다음 적은 바닥과 동기화된1860→900 좌표를 따라 자연스럽게 화면에 들어옴|
|1550~1750ms|기준 구도 정착200ms|
|1750~2030ms|상단의 네모 도트가 모여 `Stage N` 완성280ms|
|2030~2150ms|완성된 글자 유지120ms|
|2150~2250ms|글자 소멸100ms|
|2250ms|배너를 완전히 비운 뒤 입력 재개와 온전한 첫 예고|

일반 전환 총합은2250ms다. 질주만1초이며 처치 분해·Stage 표시를 포함한 전환 전체가1초라는 뜻이 아니다. 이후 길이를 조정하면 구간합과 첫 예고 시작을 함께 수정한다.

다음 적의 world anchor는1860→900으로 바닥과 동기화한다. 체급별 실루엣은 마지막150ms보다 일찍 화면에 들어올 수 있다. 마지막150ms만 표시한다는 후보는 사용자 요구사항이 아니므로 채택하지 않는다.850ms에 갑자기 표시만 켜거나 별도 속도로 적을 밀어 넣는 팝인도 추가하지 않는다. 화면에 나타났다는 이유로 공격 시계를 시작하지 않으며, 전체 전환을 마친 뒤 첫 예고를 시작한다.

## 6. Stage 배너·보스·보상·회피의 경계

큰 Stage 배너는 화면 고정 UI다. 도트는 글자의 지정된 자리로 모이며, 파편이 플레이어·위험 신호·조작 영역을 가로지르지 않게 상단 배너 영역 안에서만 움직인다. 보스의 긴 HP와 같은 공간을 동시에 쓰지 않는다. 평소 작은 Stage 표시는 큰 배너 동안 중복 노출을 피한다.

일반 적은 배너 종료 뒤 첫 전체 예고를 시작한다. 중간 보스·보스는 도착·Stage 배너 종료 → 큰 줌인 → 확대 유지/포효·무피해 공격1회 → 줌아웃/정착 → 보스HP·첫 전체 예고 순서를 권고한다. 기존 중간1.8초/보스2.2초와 재조우1.0초/1.2초, 줌1.45/1.60은 바꾸지 않는다. 배너를 포효 중 띄우거나 포효 뒤 첫 타격 시계를 미리 흐르게 하지 않는다.

전환·조립·포효 동안 전투 시계와 입력은 잠근다. 그동안 받은 공격·회피 입력은 버리고, 첫 예고가 시작한 뒤 새 누름만 받는다. 다음 적의 준비된 공격·회피 쿨타임 초기화와 첫 온전한 예고 보장은 기존 조우 계약을 유지한다.

중간/보스 처치 시 기존 보상 저장·유물3선택을 먼저 완료하고 다음 적으로 질주한다. Stage 도트 개수나 글자 완성 이벤트는 보상·체크포인트 저장을 실행하지 않는다. `Stage N`은 실제 다음 조우 데이터에서 읽고, 층 증가를 연출에서 두 번 수행하지 않는다.50층 엔딩 예외와 캐릭터별 회차·체크포인트는 그대로다.

일시정지는 Stage 조립 시계도 멈춘다. 앱 중단 후 안전한 전투 대기 상태를 복원할 때에는 미완성 글자를 이어 붙이느라 입력이 잠기지 않게 배너를 생략하거나 처음부터 다시 표시하는 한 정책으로 정한다. 어느 쪽도 층·보상·HP를 다시 변경하지 않는다. 감소 모션에서는 큰 이동·카메라 움직임 대신 이미 정한 정적 전환을 유지하고, Stage 도트는 흩어진 이동 대신 최종 글자가 짧게 나타나는 방식으로 대체한다. 조립 표시를 줄여도 게임 쪽의 첫 예고 보장과 입력 해제 순서는 같다.

회피는 전체 교체 전의 실제 `hero-dodge-up/down/front/back`으로 되돌리는 요청이다. 네 클립 모두 입력 참고1+생성16셀로 존재하며 down/back에는 기존 선별 재생 순서가 있다. 기존 down에는 v5 retry의 `lowPoseFrames`·`recoverFrames`가 없으므로 `selectedDodge`만 바꾸면 현재 높은 쓸기의 별도 안전자세 분기가 사라진다. 원본 회피 클립을 보존하면서 T~T+140ms의 위험 공간과 T+220ms 복귀가 겹치지 않는지는 시안에서 다시 시각 확인해야 한다. 위 회피의 발 높이144px·가시120px, 전방 회피와 후방 화살의 분리도 같은 기준이다. 이 롤백을 이유로 실제 회피 판정창·무적·위험 크기를 조용히 바꾸지 않는다.

## 7. v4 회피의 낮은 자세 선별과 실루엣 검수

총괄의 후속 요청에 따라 기존 네 원본 시트를 직접 확인했다. 아래 회피에는 다음 메타데이터를 붙이는 안을 권고했다. 생성 원본·기존 일반 재생 순서를 다시 만들지 않고, 위험과 겹치는 성공 회피 구간에만 별도 안전자세 순서를 지정한다.

```json
{
  "lowPoseFrames": [4, 6, 10],
  "recoverFrames": [11, 12, 13, 14, 15, 16]
}
```

T+0~139ms에 낮은 자세4→6→10을 유지하고, 위험이 퇴장하는140ms부터11~16으로 원래 복귀를 연결한다. 현재 실제 `highSweepOffsetY`는 **−24**, 즉 위쪽24px이다. 아래쪽24px로 바꾸는 안이 아니다. 가시120px·성공 점프 발 높이144px, 전방 표시 이동100px, 후방 표시 이동70px도 기존 성공 시안 기준을 사용했다.

기존 v6 모형을 메모리 안에서 네 v4 클립으로 교체하고 위 down 메타데이터만 붙여 검수했다. 실제 core 파일이나 원본 시트는 이 담당 작업에서 수정하지 않았다.

| 방향 | 직접 확인한 형태 |
| --- | --- |
|위|몸을 세워 상승한 원본 프레임이 큰 가시 끝보다 위에 남음|
|아래|다리를 벌린 낮은 자세가 칼날 아래에 머물고, 위험 퇴장 뒤 일어남|
|뒤|몸을 뒤로 빼는 자세가 정면 찌르기와 분리됨. 기존 재생 순서의 불필요한 초기 도약 제외를 유지|
|앞|낮게 앞으로 파고드는 자세가 등 뒤에 착탄한 큰 화살과 분리됨|

네 방향 각각 T+0/40/100/139ms, 총16컷에서 캐릭터 alpha와 활성 위험 alpha의 겹친 픽셀 수가0이었다. 아래 회피 T+140과219ms의 복귀도 직접 보았다. [회피 비교 이미지](../Evidence/Presentation-v7/dodge-v4-rollback-proof.png)에 네 방향의40ms와 아래 회피0/139/140/219ms를 남겼다.

이 결과는 지정된 성공 포즈의 시각 분리 확인이다. 실제 −160/−60/0ms 입력 경계, 취소·연타 중 연결, Unity의 판정·무적·애니메이션 적용을 검증한 것으로 확대하지 않는다. 원본 아래 회피의 다리 벌림 형태는 사용자가 요청한 과거 후보를 복원하는 선택이며, 새 원화를 완성했다는 뜻이 아니다.
